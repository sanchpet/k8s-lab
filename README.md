# k8s-lab

Reproducible local Kubernetes stands for testing infrastructure components before they touch a real cluster.

## Three axes

The repo is a matrix, not a tree — the axes are orthogonal and combine, they do not nest.

| Axis | Directory | Question it answers |
|------|-----------|---------------------|
| **method** | `methods/` | *How* is a cluster instantiated — kind, talos-in-docker, vcluster, k3d, lima+kubeadm. Thin wrappers, no logic of their own. |
| **env** | `envs/` | *What cluster do I get* — its construction: k8s version, node count, DNS domain, node-layer config. An env declares the method it uses. |
| **scenario** | `scenarios/` | *What do I learn about it* — the thing under test plus the checks that prove it. A scenario declares the envs it runs on. |

One method serves many envs; one env carries many scenarios; one scenario may run on several envs to see whether its conclusion survives a change of construction.
Adding an axis member is adding a directory — `methods/<name>/{up,down,reset}.sh`, `envs/<name>/` with its template and README — not editing the others.

## Layout

```
lib/common.sh          env loading, template rendering, log/die — sourced by every wrapper
methods/<method>/      up.sh / down.sh / reset.sh, each taking an env name as $1
envs/<env>/            <method>.yaml.tmpl + README (what it reproduces, where it lies)
scenarios/<scenario>/  the thing under test and its checks
.env.example           the parameter contract; copy to .env and fill in real values
```

## Quickstart

```sh
cp .env.example .env      # then edit: real values live only here, .env is gitignored
mise run up               # defaults to the onprem-kubeadm env
export KUBECONFIG=$PWD/kubeconfig-<CLUSTER_NAME>
mise run down             # or: mise run reset
```

Every task takes an env name: `mise run up onprem-kubeadm`.
Without a `.env` the wrappers fall back to `.env.example` and say so loudly — the stand comes up, but with placeholder values.

## What belongs here and what does not

This repo stays **generic and parameterized**.
Tracked files carry the shape of a problem — the mechanism, the knobs, the checks — never the identity of a particular fleet.

Out of tracked files: real DNS domains, host names and addresses, registry URLs, credentials, ticket numbers, team or employer names.
Those are `.env` values, and `.env` is not tracked.

The test is simple: a stranger should be able to clone this, fill in their own `.env`, and reproduce the mechanism without learning anything about anyone's infrastructure.

## Reproducibility

`mise run lab <scenario>` is the entry point, and it is a repair operation as much as a bring-up: it runs `up`, `apply` and `check` in order, and every step is idempotent.

That matters because two things do not survive a restart of the node containers.
The `/etc/hosts` entry a method writes into a node is regenerated by the container runtime on every start, so it is gone after a reboot.
A scenario that runs its subject without persistence loses that subject's own configuration with the pod.
Both are restored by re-running `lab`; neither is restored by running `check` alone, which is why running the checks against a stand nobody re-applied produces confident-looking nonsense.

Image archives are cached under `.cache/` so repeated runs do not re-download the same layers.
The cache is keyed by tag, not by digest, so a moving upstream tag will be served from yesterday's bytes until the entry is removed.
